# Architecture

decker is a Rust workspace with a web front-end. Rust holds the truth: the document model,
the file formats, the renderer, and during a presentation the current slide and step. The
front-end only draws what Rust sends and turns user actions into commands.

## The stack

![The stack](images/stack.svg)

| Part | Language | Role |
| --- | --- | --- |
| `crates/deck-core` | Rust | `Deck` → `Slide` → `Element`, build steps, themes, variables, JSON on disk, SVG renderer, text editing |
| `crates/deck-convert` | Rust | Library and CLI: PPTX ↔ deck, PDF, SVG render, `.deckz` archives |
| `crates/deck-typst` | Rust | Typst embedded: text, formulas, figures, PDF (feature `typst`) |
| `crates/deck-present` | Rust | The show state and the presentation windows, shared with the viewer |
| `apps/deck-app/src-tauri` | Rust | The editor application: state, commands, undo, macros |
| `apps/deck-app/src` | Svelte + TypeScript | The editor's views |
| `apps/deck-viewer` | Rust + Svelte | decker-viewer: presenting PDFs |
| `apps/shared` | Svelte + TypeScript | The presentation windows' front-end, shared by both apps |
| `python/decker` | Python | The scripting package |

A webview is the browser engine the operating system already ships, in a plain window with
no browser chrome: WebView2 (Edge's engine) on Windows, WebKitGTK on Linux.

## One source of truth

![One source of truth](images/source-of-truth.svg)

Every window subscribes to `view-changed` and re-fetches the view. Windows never talk to each
other, and no window keeps state of its own beyond what it is drawing. A Python macro gets the
same deck as JSON and hands it back; the app applies it through the state like any command.

## The presentation side, shared with the viewer

Presenting does not need the editor: it needs pages, a position in them, two windows and
keys. That part lives apart so that `decker-viewer` can present PDFs with the same windows:

- `crates/deck-present`: the show state (page, build step, blank screen) with its
  navigation over anything that reports a page count and steps per page, and the audience
  and presenter windows (created hidden at startup, placed on the monitors when the show
  starts). The editor's state delegates to it; the viewer uses it directly.
- `apps/shared`: the front-end of the two windows (`Audience.svelte`, `Presenter.svelte`),
  the slide view with media playback, the pointer, and the show protocol (`get_view`,
  `navigate`, `goto`, `start_presentation`, `stop_presentation`, `monitors`, the
  `view-changed` event) that both apps implement under the same names. The components take
  Svelte snippets to draw a page, so the editor draws SVG and the viewer draws PDF pages.

Rendering, Typst, text editing and the PDF layers are described in [Rendering and Typst](rendering.md).

## Presentation windows

![Presentation windows](images/windows.svg)

The audience and presenter windows are created at startup, hidden, alongside the editor
window; `start_presentation` lists the monitors, moves the audience window fullscreen onto
the first non-primary one and the presenter window onto the primary, and shows them. With a
single monitor only the audience window is shown. They are not created on demand: on
Windows, a webview created after startup never loaded its page (no page load event at all,
whether created from a command thread or from the main thread). The app prints `[decker]`
lines to the terminal with the monitors found and each window's page load events.

## Why these choices

- **Rust for the engine**: one fast binary on Linux and Windows, no runtime to install, and
  Python macros run in the Python found on the machine (nothing is linked, see [Python](python.md)).
- **Tauri rather than a native toolkit**: slides are text, images and shapes on a rectangle,
  which HTML and SVG render better than any widget toolkit, with fonts and GPU acceleration
  for free. Tauri uses the webview the OS already ships, so the installer stays small.
- **Svelte + TypeScript for the views**: the closest thing to plain HTML, small output, and
  the types mirror the Rust `View` so the two sides cannot drift silently.
- **JSON in a folder**: readable, diffable, and trivial to script. A zipped single file is
  the same layout archived (`.deckz`).
- **PPTX as a converter, not the native format**: import what can be expressed, warn about
  the rest, and never let PowerPoint's model dictate ours.
