# Contributing

The checks CI runs, to run before every push:

```bash
cargo fmt --all -- --check && cargo clippy --workspace --all-features --all-targets -- -D warnings && cargo test --workspace --all-features
```

```bash
python3 -I -m unittest discover -s python/tests
```

```bash
cd apps/deck-app && npm run check && npm run build
```

(and the same `npm` checks in `apps/deck-viewer`).

Every change to the code comes with the matching change to this manual, in the same commit.
The [commands and keys](keys.md) page is generated from the editor's help list
(`apps/deck-app/src/lib/Help.svelte`): after changing that list, run

```bash
python3 docs/gen_keys.py
```

(`--check` fails when the page is stale.)

The fixture `tests/fixtures/fixture.pptx` is generated by python-pptx; the tests import it
and round-trip a deck through export and import.

## Documentation

The manual is an [mdBook](https://rust-lang.github.io/mdBook/) in `docs/`, the API reference
is rustdoc. Rust's equivalent of Sphinx is this pair: rustdoc builds the reference from doc
comments (`///`) like autodoc, mdBook builds the narrative pages from Markdown.

```bash
cargo install mdbook
```

```bash
mdbook serve docs            # live preview at http://localhost:3000
```

```bash
cargo doc --no-deps -p deck-core -p deck-convert -p deck-typst --open
```

The diagrams are generated:

```bash
python3 docs/diagrams/generate.py
```

CI builds both on every push and publishes them to GitHub Pages from `main`. The manual is at
`/decker/` and the API reference at `/decker/api/`.

## Releases

The `Installers` workflow builds the Windows (NSIS, per user) and Linux (deb, AppImage)
installers of both applications on every push and keeps them as artifacts of the run.
Pushing a tag `vX.Y.Z` also publishes them as a GitHub release with generated notes:

```bash
git tag v0.1.0 && git push origin v0.1.0
```

The `Python package` workflow builds `decker-slides` on every push, checks its metadata and
runs the tests against the installed wheel; on a `vX.Y.Z` tag it also publishes it to PyPI.
Bump `version` in `python/pyproject.toml` before tagging. Publishing uses PyPI's trusted
publishing, so no token is stored in the repository; it needs a one-time setup by the
project's owner:

1. On PyPI, under *Your account → Publishing*, add a pending publisher for the project
   `decker-slides`: owner `gbegou`, repository `decker`, workflow `pypi.yml`,
   environment `pypi`.
2. On GitHub, under *Settings → Environments*, create the environment `pypi` (optionally
   restricted to tags `v*`).

The manual is published by the `Docs` workflow to GitHub Pages, which has to be enabled once
in the repository's settings (Pages, source "GitHub Actions").

## Screenshots

The manual's screenshots (`docs/src/images/screens/`) are taken from the real editor, driven
over WebDriver, on a demo deck built by `docs/screenshots/make_demo.py`:

```bash
docs/screenshots/shoot.sh
```

It needs Linux (it starts Xvfb when there is no display), `tauri-driver`
(`cargo install tauri-driver`), WebKitWebDriver (package `webkit2gtk-driver`) and ImageMagick.
Each shot is a function in `docs/screenshots/shoot.py` with its own app start; retake them
when the interface changes, and add one for a new feature that is easier shown than told.
